# Transactional updates

An update that finishes leaves the machine running the code it just replaced.
`omarchy-server-update-restart` deals with that by restarting what changed
(`docs/iso-server.md` §3.1, `reports/2026-08-29-update-without-reboot.md`), and
for the overwhelming majority of updates that is the right answer: no reboot,
no window, nothing to schedule.

What it cannot deal with is an update that *breaks*. A `pacman -Syu` that dies
halfway leaves the running root half-new, and the recovery is a snapper
snapshot, a reboot into it and a manual rollback — on a machine nobody is
logged into.

The transactional mode removes that case. The update runs inside a writable
snapshot of the root subvolume, with the shared parts of the machine bound in,
and the live root is never opened for writing. If it fails, the snapshot is
deleted and the machine is exactly what it was. If it succeeds, the snapshot
*becomes* the root at the next reboot.

```bash
sudo omarchy-server-update --transactional      # this run only
sudo omarchy-server-update transactional on     # and every run after it, timer included
sudo omarchy-server-update status               # which mode, and what the last transaction did
sudo omarchy-server-update rollback             # boot the previous root again
```

The mode ships **off**. A transaction is always a reboot, and opting a fleet
into a reboot is not a default anyone should get by accident.

## What it does, in order

1. **A snapper snapshot of the live root**, exactly as an in-place update takes
   one. It is what the Limine menu offers, and it is taken first so it is a
   picture of the machine as it was.
2. **A writable btrfs snapshot of `@`**, named `@tx-<timestamp>`.
3. **The shared parts bound into it** — `/boot` (the ESP), `/var/log`,
   `/var/cache/pacman/pkg`, `/home`, and `/proc`, `/sys`, `/dev`, `/run`,
   `/tmp`. Those first four are not part of the root subvolume and must be the
   same object inside the transaction as outside it: the UKI the hooks write is
   the one the machine boots, the update's own log survives a discarded
   transaction, and nothing is downloaded twice.
4. **The update, inside the chroot**: `pacman -Syu`, then anything named by
   `--with`, then the profile's post-steps — migrations, the `post-update`
   hook, `paccache -rk2`.
5. **The swap**, if all of that succeeded. Two renames (below).
6. **The reboot**, or `--kexec` when the `kexec` addon is present, or nothing at
   all with `--no-reboot`.

`omarchy-server-update-restart` does not run in this mode and has nothing to do:
no file under the running root moved, so no process is running replaced code.

## How the new root is selected

By renaming subvolumes, not by changing the boot configuration:

```
@          ->  @prev-<ts>      the root that was running
@tx-<ts>   ->  @               the root the transaction built
```

The kernel command line, the UKI, `/etc/fstab` and every pacman hook stay byte
for byte what they were. That is the whole point: nothing about the boot path
changes, so nothing about the boot path can regress — including under Secure
Boot, where the signed chain is untouched.

The two alternatives were both worse here.

`btrfs subvolume set-default` does nothing: the command line carries
`rootflags=subvol=@` explicitly (`/etc/kernel/cmdline`, `/etc/default/limine`,
and every entry `limine-entry-tool` writes), and an explicit `subvol=` beats the
filesystem default.

Pointing the Limine entry at the new subvolume works — `limine-snapper-sync`
already does it for snapshot entries — but it means rewriting three files on
every transaction, and all three are regenerated by a pacman hook *inside* the
transaction trying to change them. It also makes the machine's boot
configuration drift by one name per update.

### The two things a rename does not carry

**Nested subvolumes.** A btrfs snapshot is not recursive, so `.snapshots`,
`var/lib/machines` and `var/lib/portables` arrive in the new root as empty
directories. `.snapshots` is the record of every snapper snapshot the machine
has, so the swap re-creates it and re-snapshots each retained snapper snapshot
into it — read-only reflinks, metadata only. The other two are empty by
definition and are re-created as subvolumes.

**The ESP.** `/boot` is one vfat partition shared by every root, so the
mkinitcpio and sbctl hooks inside the transaction overwrite the UKI the
*currently running* kernel boots from. Fine going forward, fatal going
backwards. The pre-transaction UKI and `limine.conf` are therefore copied to
`/boot/omarchy-tx/prev/` before the transaction starts. A failed transaction
restores them immediately; a rollback restores them before swapping the names
back. They were signed when they were saved, so nothing is re-signed on the way
out.

## Rollback

```bash
sudo omarchy-server-update rollback
```

The same two renames in the other direction, plus the saved ESP files copied
back:

```
@              ->  @failed-<ts>
@prev-<ts>     ->  @
```

Then a reboot. The root that failed is kept as `@failed-<ts>` so its logs and
its `/etc` are still readable; `omarchy-server-transaction prune` removes it.

Rollback works from the running system. If the machine does not boot at all,
the Limine menu still offers the snapper snapshots it always did — and the
snapshot taken in step 1 is the same state `@prev-<ts>` is.

## Secure Boot

Nothing special is required and nothing is signed by hand. The sbctl keys live
at `/var/lib/sbctl`, which is on the root subvolume and therefore inside the
transaction; the ESP is the same partition either side. `mkinitcpio` builds the
UKI inside the chroot, the sbctl post hook signs it there, `limine-entry-tool`
writes the entry with the hash of the signed file, and the machine boots it.
Measured: `reports/2026-08-29-transactional-updates.md`, items 17–22.

One fact that surfaced while choosing the mechanism and belongs on the record:
**the UKI on this profile carries no embedded `.cmdline` section**, so the
command line Limine passes is the command line the kernel gets, Secure Boot or
not. The `lockdown=integrity module.sig_enforce=1` this profile relies on is in
`limine.conf` on the ESP, not inside the signature.

## SELinux

Reasoned, **not measured** — see the limitations of the report. A btrfs snapshot
shares the metadata of the subvolume it was taken from, `security.*` xattrs
included, so no relabel is implied by the snapshot or by the rename. `/boot` and
`/var/log` are bind mounts of the live objects, so their labels cannot change.
Files pacman *creates* inside the chroot are labelled by the policy loaded in
the running kernel, which is exactly the situation an in-place update is already
in. That enforcing survives a transactional kernel update has not been run.

## Installing packages transactionally

```bash
sudo omarchy-server-transaction run --with docker --with docker-compose
```

`--with` installs or reinstalls named packages inside the transaction, after the
upgrade. It is how anything that changes the package set gets to be
transactional too — an addon, a one-off `pacman -S`, or a kernel reinstall to
force a fresh initramfs — without ever writing to the running root.

`omarchy-server-addon` does **not** go through this yet: it still writes to the
running root.

## The command

```
omarchy-server-transaction <run|rollback|status|prune|discard> [flags]

  run       build a transaction, update inside it, swap it in and reboot
  rollback  swap the previous root back in and reboot
  status    which root is running, what the last transaction did
  prune     delete all but the --keep most recent previous roots
  discard   delete an unswapped @tx-* left by --no-swap or a killed run

  --with PKG    also install/reinstall PKG inside the transaction (repeatable)
  --keep N      previous roots to retain (default 1)
  --no-swap     build and update the transaction, do not swap it in
  --kexec       take the reboot with kexec into the signed UKI
  --no-reboot   swap the names and leave the reboot to someone else
```

`status` reads the transaction record out of `@` rather than out of `/`, so a
machine that has swapped but not yet rebooted reports the transaction that is
waiting and says which root it is actually running.

## What it costs

Measured on a 4 vCPU KVM guest with the package already in the cache
(`reports/2026-08-29-transactional-updates.md`):

| Transaction | Wall clock | Filesystem `Used` delta |
|---|---|---|
| nothing to upgrade | 3 s | +1.2 MiB |
| one small package | 3 s | +1.3 MiB |
| kernel reinstall (initramfs + UKI + signature) | 8–12 s | +173 MiB |

The floor is the snapshot, which is reflinked and costs metadata only. The
kernel figure is a new `/usr/lib/modules` tree and a new 38 MiB UKI, held twice
for as long as `@prev-<ts>` is kept — `--keep 1` by default, so the steady-state
cost of the mode is one previous root. The ESP does not grow: the saved copy
replaces the previous saved copy.

Reboot round trip on that VM: 10–11 s.

## Limitations

**The swap is not atomic.** Two renames, two syscalls, nothing between them;
btrfs offers no atomic rename pair. For the width of that window the filesystem
has no subvolume called `@`, and losing power inside it drops the next boot into
the initramfs emergency shell. The repair is one line, from that shell or from
any live ISO:

```bash
mount /dev/<root-partition> /mnt -o subvolid=5
ls /mnt                     # @prev-<ts> and @tx-<ts> will both be there
mv /mnt/@prev-<ts> /mnt/@   # or `mv /mnt/@tx-<ts> /mnt/@` to keep the update
umount /mnt && reboot
```

Every alternative that closes the window trades it for a boot configuration
that changes on every update, which is a much larger surface to get wrong.

**A transaction is always a reboot.** That is the trade the mode makes, and it
is why the mode ships off. A fleet that updates weekly and cannot reboot weekly
wants the in-place mode and its restart classifier.

**Orphan removal is not part of a transaction.** `omarchy-update-orphan-pkgs`
needs a terminal to confirm with, and an unattended run reports and moves on;
the transaction does not run it at all.

**`.snapshots` is re-created on every swap.** The snapper snapshots survive —
they are re-snapshotted into the new root — but their subvolume ids change.
Nothing on this profile keys off those ids. The cleaner layout is `@snapshots`
as a top-level subvolume mounted by fstab, which is what openSUSE does; it
would remove the loop entirely and is an installer change with a migration.

**Rollback has only been proved across a kernel *reinstall*, not a kernel
version change.** See the report.
