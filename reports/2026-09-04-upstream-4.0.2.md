# Upstream bump: omarchy v4.0.2

**Date:** 2026-09-04
**Subject:** moving the pin from the `quattro` tip (`468b511`) to the release tag `v4.0.2` (`346e69e`), packaging it, and proving the result on a booted machine
**Result:** 19/19 patches apply, `make test` green, all three packages built and signed, 85/85 packaging assertions, 16/17 router acceptance items on the VM (the one miss is the test machine's own state, not the release)

## Scope

This is the first bump on the `tags` channel. The previous pin was a commit on
the upstream default branch, taken before `upstream/PIN` existed; this one is a
release tag, which is what `docs/maintenance.md` says the profile should
follow.

What is established here, in order: the patch series still applies to the new
upstream tree, the profile's own tests still pass against it, the three
packages build and sign from the new commit, the packaging acceptance passes,
and a machine that was running the previous release upgrades to this one and
still behaves like the profile promises.

The ISO is not rebuilt here. The ISO patch series is proven to apply (below),
but a built ISO and a from-scratch install are a separate run.

## What moved upstream

| | from | to |
|---|---|---|
| omarchy | `468b511` (branch tip) | `346e69e` (tag `v4.0.2`) |
| omarchy-iso | `268bac1` | `2673c61` (default branch; the repository publishes no tags) |

Between the two release tags: **28 commits, 167 files, +10486 / -497**. Most of
that is tests — the non-test tree is 50 files and +2859 / -325. The release is
overwhelmingly a security release, and the parts of it that reach a headless
machine are these:

**The `[omarchy]` pacman repository now requires signatures.** `SigLevel =
Optional TrustAll` is gone from all three channel templates
(`pacman-{stable,rc,edge}.conf`), so packages from that repository are verified
against the omarchy signing key like any other. `pacman-rc.conf` also stops
pointing at the edge channel and points at `rc`.

**SSH hardening now closes password authentication.**
`omarchy-setup-security-sshd` writes an `sshd_config.d` drop-in turning
`PasswordAuthentication` and `KbdInteractiveAuthentication` off — but only
after a key is authorized, validating with `sshd -t` and then re-reading the
*effective* config with `sshd -T`, and removing the drop-in again if either
check fails. It reloads rather than restarts, so a connected administrator
keeps their session. A migration applies the same to machines already
installed. For a profile whose only login path is sshd this is the most
consequential change in the release, and it is one the profile wanted anyway.

**Privileged group defaults are no longer replayed at first boot.**
`omarchy-provision-owner` already refused to grant `docker` from a recorded
group list; it now also drops `input` unless the image actually carries one of
the packages that needs raw input devices. Both are desktop concerns, but the
code path is the one a deferred-provisioning server install runs.

**Base package list:** `cups-browsed` and `cups-pdf` out, `cups-pk-helper` in.
None of the three is in the server base.

**Ten new migrations** (sshd hardening, the input group, retired installer
artifacts, legacy power udev rules, browser policy directories). The runtime
package pre-marks every migration in `/etc/skel`, so a fresh user replays none
of them; there are now 96 stubs.

The rest is desktop surface the profile does not ship or does not run: webapp
install escaping, plymouth, themes, the Windows VM mount boundary, browser
policy directories, the Apple brightness device cache, cups-browsed hardening.

### The signature change, verified

The one upstream change with a plausible way to break this profile is the
`[omarchy]` repository dropping `SigLevel = Optional TrustAll`: the server base
pulls `limine-mkinitcpio-hook`, `limine-snapper-sync`, `ufw-docker`, `tzupdate`
and `yay` from there, and a machine without the upstream signing key would stop
being able to install any of them.

The settings package at 4.0.2-1 ships the new templates, with no per-repository
`SigLevel` and the global default at `Required DatabaseOptional`. On the
upgraded machine, `pacman -Sy` followed by a download of an `[omarchy]` package
completed through "checking keyring / checking package integrity" with no
error: `omarchy-keyring` is a dependency the profile already installs, and its
key is in the pacman keyring beside the profile's own. **No action needed.**

## sshd password lockout in v4.0.2

**Date:** 2026-09-04
**Subject:** what upstream's new sshd hardening migration does to a headless
server when it arrives through an in-place update
**Result:** on an upgraded server the migration **disables and stops sshd**, and
the machine is then unreachable. This is a blocking finding for the bump.

### What upstream ships

Two pieces, both new in v4.0.2:

`bin/omarchy-setup-security-sshd` gained a `disable_password_auth` step. It
writes `/etc/ssh/sshd_config.d/10-omarchy-hardening.conf` with
`PasswordAuthentication no` and `KbdInteractiveAuthentication no`, but only
after a key was authorized in the same run. It validates with `sshd -t`, then
re-reads the effective config with `sshd -T`, removes the drop-in again if
either check fails, and reloads rather than restarts. That command is
interactive and nothing on a server calls it, so it is not the problem.

`migrations/1788124236.sh` is the problem. Its own first line reads: "Disable
SSH password authentication, or sshd itself when no key is authorized." The
logic, in order:

1. Exit if `10-omarchy-hardening.conf` already exists (that file is the
   machine-wide completion state).
2. Exit if `sshd.service` is neither enabled nor active.
3. Read `$HOME/.ssh/authorized_keys` and ask whether any single line parses as
   a public key.
4. **If no usable key is found, run `systemctl disable --now sshd.service`**,
   print a notice, and exit 0.
5. Only with a usable key does it install the drop-in, validate it with
   `sshd -t` and `sshd -T`, and reload sshd.

So it does check for an authorized key. The check is just asked of the wrong
account.

### Why that check answers wrong on a server

`omarchy-migrate` keeps per-user markers under
`~/.local/state/omarchy/migrations` and reads `$HOME` for the key check. On a
headless machine the update runs as **root**: the update service declares
`Environment=HOME=/root`, exactly so the timer and a hand-run `sudo
omarchy-server-update` share one state directory, and the transaction script
calls `omarchy-migrate` from there.

Root on this profile has no authorized key, and is not supposed to have one.
The profile sets `PermitRootLogin no`; administrators log in as a named account
and escalate. The migration therefore reaches step 4 for the one account whose
answer decides the fate of the daemon every other account depends on.

`install/server/root-migration-state-server.sh` already pre-marks every shipped
migration for root at install time, precisely because desktop migrations should
not replay against `/root`. That seeding runs **once, during install**. Any
migration that arrives later with a package upgrade is unmarked and pending for
root, which is how this one gets to run at all.

### Measured on a lab VM

A router-profile VM running `omarchy-server 4.0.1-20` /
`omarchy-server-settings 4.0.1-9`, reachable only over ssh. Before the upgrade,
`sshd -T` already reported `passwordauthentication no`,
`kbdinteractiveauthentication no`, `permitrootlogin no`, all from the profile's
own `10-omarchy-server.conf`, and a password login attempt against a throwaway
local account with a valid password was refused with
`Permission denied (publickey)`. The machine was already password-free before
upstream's migration touched it.

Then the locally built `omarchy-server 4.0.2-1` and
`omarchy-server-settings 4.0.2-1` were installed with `pacman -U`, and
`omarchy-migrate` was run as root with `HOME=/root`, which is what
`omarchy-server-update run` does at its `== migrations` step.

Nine migrations were pending for root. All nine ran. The last one:

```
Running migration (1788124236)
Disable SSH password authentication, or sshd itself when no key is authorized
Removed '/etc/systemd/system/multi-user.target.wants/sshd.service'.
No usable SSH key is authorized, so sshd only accepted password logins. The SSH
server has been disabled: run omarchy-setup-security-sshd to set it up with
key-based authentication, or re-enable sshd to accept password logins anyway.
```

State immediately after:

| | before | after |
|---|---|---|
| `systemctl is-enabled sshd` | `enabled` | `disabled` |
| `systemctl is-active sshd` | `active` | `inactive` |
| `10-omarchy-hardening.conf` | absent | still absent |
| `sshd -T` password settings | already `no` | unchanged, `no` |

`/root/.ssh/authorized_keys` existed and was zero bytes, which the migration
reads the same way as no file at all.

`omarchy-migrate` exited 0 and the marker was written, so the migration is done
and will never retry. Nothing on the machine puts sshd back. On a real headless
box the run ends there and the only remaining way in is a console. The lab run
re-enabled sshd from a detached script on purpose, to be able to collect the
evidence.

The counter-case was measured too. With a usable public key placed in
`/root/.ssh/authorized_keys` and the marker cleared, the same migration takes
its other branch: it writes `10-omarchy-hardening.conf`, passes `sshd -t` and
`sshd -T`, reloads sshd, and the daemon stays up. Key login kept working and
the password attempt was still refused. The drop-in is harmless there and also
redundant, since it only restates what `10-omarchy-server.conf` already sets
(it sorts ahead of it, so it wins the first-value rule with identical values).

### What the tools report

`tui-secure --check` on the machine with sshd disabled shows it in the stack
line, `"sshd": "sshd: stopped"`. That is the only signal, and it reads as a
posture note rather than as an outage.

`tui-ssh --check` reports `"effective": true` and every keyword `ok`
(`PermitRootLogin no`, `PasswordAuthentication no`,
`KbdInteractiveAuthentication no`, `PermitEmptyPasswords no`, all sourced to
`10-omarchy-server.conf`), with only `MaxAuthTries` and `LoginGraceTime` as
warnings. It reads the configuration, not the unit, so a stopped daemon looks
perfectly configured. Neither tool would tell an operator that the machine just
stopped accepting logins, though `tui-secure`'s stack line is the closest
thing.

### Blast radius

- **In-place upgrades from an earlier release are affected.** That is every
  installed machine, and the daily update timer takes the same path unattended.
- **From-scratch installs of 4.0.2 are not affected.** The install seeds root's
  markers from the shipped migration set, so this one is marked before it can
  run.
- **Named accounts are not affected.** Their `authorized_keys` has a key, so
  they get the benign branch. Only root answers the key question wrong, and
  root is the account the update runs as.
- The other eight migrations that ran as root were desktop concerns (browser
  policy directories, CUPS, the `input` group, retired installer artifacts,
  XCompose and Omarchy 3 power udev rules, the rc channel). None of them failed
  here, but they are the same class of thing the install-time seeding exists to
  keep away from `/root`.

### Proposed guard

Both halves are worth having; the first is what blocks the bump.

**1. Patch the migration, in the profile's patch series.** The intent upstream
is closing a password-only SSH server that an aborted setup left exposed. That
condition cannot exist on this profile: `10-omarchy-server.conf` sets
`PasswordAuthentication no` and `KbdInteractiveAuthentication no` from the
install onward. The patch should make the "no usable key" branch inert whenever
sshd's *effective* configuration already refuses passwords, asking `sshd -T`
the same question the migration's own success path asks, and exit 0 with a
notice instead of disabling the daemon. A machine that genuinely accepts
passwords still gets upstream's treatment; a key-only server is never taken
offline by a check performed against an account that is not allowed to log in
anyway. This keeps the fix in one file that rebases with the series.

**2. Re-seed root's migration markers on package upgrade, not only at
install.** The reasoning in `root-migration-state-server.sh` (migrations are
written for a desktop session, and the profile ships current) does not stop
being true when a migration arrives by upgrade instead of by ISO. A pacman
`post_upgrade` hook on `omarchy-server` that marks any newly shipped migration
for root would have prevented all nine from running here. This is the systemic
fix and it is also a policy decision, since it opts the profile out of future
upstream migrations by default; it should be taken deliberately rather than as
a side effect of this bump.

A pre-check in `omarchy-server-update` (record whether sshd was enabled before
migrations, restore and warn if it was disabled) was considered and is weaker:
it repairs after the fact, inside the same run that may also reboot, and it
does nothing for `omarchy-migrate` invoked by hand.

### Fix applied: guard 1, as a patch in the series

`profile/server/overlay/patches/0007-sshd-migration-keep-keyonly-server.patch`.
It touches only the "no usable key" branch of `migrations/1788124236.sh`, and
only to ask sshd a question before acting on an answer given by an account that
cannot log in. The key-present branch is upstream's, unchanged.

The branch now reads `sshd -T` first, the same way the migration's own success
path does, and then:

- **passwords already refused** (`passwordauthentication no` and
  `kbdinteractiveauthentication no`): there is no password-only server to close,
  so the migration prints a notice and exits 0 with sshd untouched. That is the
  state `10-omarchy-server.conf` installs, so this is the branch every machine
  on this profile takes.
- **invoked by root on a machine with `PermitRootLogin no`**: root cannot have
  a usable key by policy, so its empty `authorized_keys` says nothing about the
  machine. Notice, exit 0, sshd untouched.
- **anything else**: upstream's behaviour, including a machine that genuinely
  accepts passwords with no key authorized, and including a `sshd -T` that
  cannot be read — an unknown answer is not treated as a safe one.

`test/shell.d/sshd-migration-patch-test.sh` rebuilds the patched migration the
way the package does (the upstream file at the pinned commit, plus the patch)
and walks all four cases against stubbed `sshd`, `systemctl`, `ssh-keygen`,
`sudo` and `install`: key-only server not disabled, unusable `authorized_keys`
not disabled, password-accepting server still disabled with upstream's notice,
root under `PermitRootLogin no` not disabled, and the key-present branch still
writing and validating the drop-in and reloading rather than disabling. The
root case runs under `unshare -r` for a real EUID 0. `make test` is green,
5 test files.

`pocs/server-install/acceptance.sh` and `acceptance-router.sh` both gained
**"sshd enabled and active after update"**, which reads the unit state rather
than the configuration. The existing sshd checks all read `sshd -T`, and this
finding is precisely a case where the configuration is perfect and the daemon
is gone.

Guard 2 (re-seeding root's migration markers on package upgrade) is still open.
It is a policy decision about future upstream migrations, not a fix for this
one, and it is deliberately not part of this bump.

### Status

Fixed in this branch. The blocking condition is closed: an in-place update on
this profile no longer disables sshd. Proved by the shell test above; the same
VM run that measured the lockout is owed against the patched packages.
