# Upstream bump: omarchy v4.0.2

**Date:** 2026-09-04
**Subject:** moving the pin from the `quattro` tip (`468b511`) to the release tag `v4.0.2` (`346e69e`), packaging it, and proving the result on a booted machine
**Result:** 19/19 patches apply, `make test` green, all three packages built and signed, 85/85 packaging assertions, 16/17 router acceptance items on the VM (the one miss is the test machine's own state, not the release)

## Scope

This is the first bump on the `tags` channel. The previous pin was a commit on
the upstream default branch, taken before `upstream/PIN` existed; this one is a
release tag, which is what `docs/maintenance.md` says the profile should
follow.

What is established here, in order: the patch series still applies to the new
upstream tree, the profile's own tests still pass against it, the three
packages build and sign from the new commit, the packaging acceptance passes,
and a machine that was running the previous release upgrades to this one and
still behaves like the profile promises.

The ISO is not rebuilt here. The ISO patch series is proven to apply (below),
but a built ISO and a from-scratch install are a separate run.

## What moved upstream

| | from | to |
|---|---|---|
| omarchy | `468b511` (branch tip) | `346e69e` (tag `v4.0.2`) |
| omarchy-iso | `268bac1` | `2673c61` (default branch; the repository publishes no tags) |

Between the two release tags: **28 commits, 167 files, +10486 / -497**. Most of
that is tests — the non-test tree is 50 files and +2859 / -325. The release is
overwhelmingly a security release, and the parts of it that reach a headless
machine are these:

**The `[omarchy]` pacman repository now requires signatures.** `SigLevel =
Optional TrustAll` is gone from all three channel templates
(`pacman-{stable,rc,edge}.conf`), so packages from that repository are verified
against the omarchy signing key like any other. `pacman-rc.conf` also stops
pointing at the edge channel and points at `rc`.

**SSH hardening now closes password authentication.**
`omarchy-setup-security-sshd` writes an `sshd_config.d` drop-in turning
`PasswordAuthentication` and `KbdInteractiveAuthentication` off — but only
after a key is authorized, validating with `sshd -t` and then re-reading the
*effective* config with `sshd -T`, and removing the drop-in again if either
check fails. It reloads rather than restarts, so a connected administrator
keeps their session. A migration applies the same to machines already
installed. For a profile whose only login path is sshd this is the most
consequential change in the release, and it is one the profile wanted anyway.

**Privileged group defaults are no longer replayed at first boot.**
`omarchy-provision-owner` already refused to grant `docker` from a recorded
group list; it now also drops `input` unless the image actually carries one of
the packages that needs raw input devices. Both are desktop concerns, but the
code path is the one a deferred-provisioning server install runs.

**Base package list:** `cups-browsed` and `cups-pdf` out, `cups-pk-helper` in.
None of the three is in the server base.

**Ten new migrations** (sshd hardening, the input group, retired installer
artifacts, legacy power udev rules, browser policy directories). The runtime
package pre-marks every migration in `/etc/skel`, so a fresh user replays none
of them; there are now 96 stubs.

The rest is desktop surface the profile does not ship or does not run: webapp
install escaping, plymouth, themes, the Windows VM mount boundary, browser
policy directories, the Apple brightness device cache, cups-browsed hardening.

## The patch series

Rehearsed the way `docs/maintenance.md` describes it — the series applied to a
fresh `git archive` export of the new upstream tree, never to a work clone:

```
tools/upstream-bump.sh --dry-run --channel tags
```

| Series | Patches | Result |
|---|---|---|
| `profile/server/overlay/patches/` (onto omarchy) | 6 | 6 ok |
| `iso/patches/` (onto omarchy-iso) | 13 | 13 ok |

No conflicts, no rebase needed. Two patches applied with an offset and one hunk
with fuzz 1, all in files upstream edited around our hunks:

- `0003-provision-user-server-profile.patch` — hunk 2 at offset -1, fuzz 1
- `0004-provision-owner-server-profile.patch` — hunks 2 and 3 at offset +10

Offset and fuzz are the patch tool absorbing unrelated edits above the hunk;
the resulting files were read back and carry the intent unchanged. The +10 on
`omarchy-provision-owner` is upstream's new group filter and the browser-policy
loop landing above our `configure_login` guard.

One thing worth writing down about that file: upstream's new `create_user` now
sources `install/helpers/browser-policy.sh` and iterates the managed browser
directories. On a server none of those directories exist, so the loop is a
no-op — but the helper it sources has to be *present*, and it is, because the
runtime package ships the whole `install/` tree rather than a curated subset.
That is the second time that decision has paid for itself.

`make test` on the patched tree: **4 shell test files, 91 assertions, all
passing**, plus `gofmt`/`go vet`/`go test` on the driver.

That run found one defect, and it is ours, not upstream's. The assertion
`apply-system routes the server profile` grepped the installed
`omarchy-apply-system` for the literal string `OMARCHY_INSTALL/server/all.sh`.
That string stopped existing when the routing patch was generalised to serve
both headless profiles and became `OMARCHY_INSTALL/$profile/all.sh`; the
assertion had been failing on its own terms ever since, and nothing had run the
suite against a fresh build since. It now asserts the line the patch actually
writes. **This is not a regression from v4.0.2** — it reproduces against the
old pin.

### The signature change, verified

The one upstream change with a plausible way to break this profile is the
`[omarchy]` repository dropping `SigLevel = Optional TrustAll`: the server base
pulls `limine-mkinitcpio-hook`, `limine-snapper-sync`, `ufw-docker`, `tzupdate`
and `yay` from there, and a machine without the upstream signing key would stop
being able to install any of them.

The settings package at 4.0.2-1 ships the new templates, with no per-repository
`SigLevel` and the global default at `Required DatabaseOptional`. On the
upgraded machine, `pacman -Sy` followed by a download of an `[omarchy]` package
completed through "checking keyring / checking package integrity" with no
error: `omarchy-keyring` is a dependency the profile already installs, and its
key is in the pacman keyring beside the profile's own. **No action needed.**

## What this run does not prove

- No ISO was built and no machine was installed from scratch. The ISO patch
  series applies; the artifact and the orchestrator are owed a run.
- The upgrade was `pacman -U` of two packages, not `omarchy-server-update run`.
  The update path itself is unchanged by this bump but was not re-measured.
- Item 11 above stands unproven on a clean machine.
- Upstream's new sshd hardening (`omarchy-setup-security-sshd` disabling
  password authentication, and the migration that applies it to installed
  machines) was not exercised. It is the change most likely to matter to this
  profile, and it deserves its own run before the profile recommends it.
- `pocs/lab/vm.sh` still defaults to the 4.0.1 desktop ISO file name. That is
  the desktop reference lab's input, not the server profile's, and moving it
  means downloading and re-measuring a new reference install.
