# ZFS as a signed kernel module under Secure Boot — started, paused

**Date:** 2026-08-29
**Status:** paused after the feasibility measurement, before any packaging was
written. Reprioritised behind SELinux.
**Raw evidence:** [`pocs/server-install/reference/module-signing-keyrings.txt`](../pocs/server-install/reference/module-signing-keyrings.txt)

The goal was an opt-in `zfs` addon whose kernel module loads on a machine with
Secure Boot enforcing — the Quave ONE case, where `zfs-localpv` snapshots are
shipped to S3-compatible storage. The first question that had to be answered was
whether a module signed by a key this profile controls is accepted at all. It is
not, and the measurement below is why the rest of the work was not started.

---

| | |
|---|---|
| Machine | lab VM `srvsb`, `LAB_OUT=pocs/lab/out-server-secboot`, ssh port 2204 |
| Firmware | OVMF `OVMF_CODE_4M.secboot`, PK cleared at create time (`vm.sh --secboot`), machine's own PK/KEK/db enrolled during the install |

## The keyring facts, measured

### 1. Certificates from the UEFI `db` land in `.platform`, not `.machine`

The kernel logs them individually at boot:

```
[    0.161280] integrity: Platform Keyring initialized
[    0.161281] integrity: Machine keyring initialized
[    0.202680] integrity: Loading X.509 certificate: UEFI:db
[    0.204338] integrity: Loaded X.509 cert 'Database Key: 00eb1ef918ef8f440a3f2094f27c5078b5'
```

`Database Key` is this machine's own sbctl certificate
(`/var/lib/sbctl/keys/db/db.pem`, `CN=Database Key`, SHA-1
`31:9D:7B:93:3A:C9:E2:30:A1:FE:2D:53:41:1F:2F:CA:D4:35:EB:C1`). `keyctl` shows
where it actually went:

```
--- %:.machine
Keyring
 522222311 ---lswrv      0     0  keyring: .machine          ← EMPTY

--- %:.platform
 840998113 ---lswrv      0     0  keyring: .platform
 713870287 ---lswrv      0     0   \_ asymmetric: Database Key: 00eb1ef918ef8f440a3f2094f27c5078b5
 ... the five Microsoft CAs enroll-keys --microsoft added ...

--- %:.secondary_trusted_keys
 764340048 ---lswrv      0     0  keyring: .secondary_trusted_keys
 278072265 ---lswrv      0     0   \_ keyring: .builtin_trusted_keys
 972155036 ---lswrv      0     0       \_ asymmetric: Build time autogenerated kernel key: b1dabbe…
```

`.machine` is initialised and empty. `.secondary_trusted_keys` links
`.builtin_trusted_keys` and nothing else. Module signature verification consults
the builtin and secondary keyrings (and `.machine` through the latter); it never
consults `.platform`, which exists for kexec images and dm-verity roothash
signatures. `CONFIG_INTEGRITY_MACHINE_KEYRING=y` does not change this: `.machine`
is fed from shim's `MokListRT`, and this machine has no shim — `/sys/firmware/efi/efivars`
contains no `Mok*` variable at all.

### 2. A module signed by the `db` key is refused

Three loads of the same module, on the running enforcing system:

| Module | Signer | `insmod` | Kernel |
|---|---|---|---|
| `dummy.ko` as shipped | `Build time autogenerated kernel key` | **loads** | — |
| signature stripped | none | **refused** | `Loading of unsigned module is rejected` |
| re-signed with `/var/lib/sbctl/keys/db/db.{key,pem}` | `Database Key` | **refused** | `Loading of module with unavailable key is rejected` |

The first row is the control: `module.sig_enforce=1` is real and in-tree modules
are fine. The third row is the answer — the exact certificate the firmware has in
`db`, and which the kernel logged loading, buys nothing for a module.

### 3. No certificate can be added to a module-trusted keyring at runtime

```
%:.machine                 add_key: Permission denied
%:.secondary_trusted_keys  add_key: Required key not available
%:.platform                add_key: Permission denied
%:.builtin_trusted_keys    add_key: Permission denied
```

`.secondary_trusted_keys` answers differently from the others and the difference
is the whole story: it would accept a certificate that is itself signed by a key
already in the builtin or machine keyring. The only key in `.builtin_trusted_keys`
is Arch's *build-time autogenerated* one, whose private half is generated and
discarded inside the Arch build. There is nothing to sign a certificate with.

Relevant config, read from `/proc/config.gz` on the running kernel:

```
CONFIG_INTEGRITY_PLATFORM_KEYRING=y
CONFIG_INTEGRITY_MACHINE_KEYRING=y
CONFIG_LOAD_UEFI_KEYS=y
CONFIG_SECONDARY_TRUSTED_KEYRING=y
CONFIG_MODULE_SIG_KEY="certs/signing_key.pem"
# CONFIG_MODULE_SIG_FORCE is not set
# CONFIG_INTEGRITY_CA_MACHINE_KEYRING is not set
# CONFIG_SECONDARY_TRUSTED_KEYRING_SIGNED_BY_BUILTIN is not set
```

## What this rules out

Both routes the task set out to compare fail for the same reason, and the reason
has nothing to do with which of them builds the module:

- **(a) prebuilt `zfs-linux`, signed in CI with an `omarchy-server-modules` key
  enrolled into firmware `db`.** Enrolling into `db` puts the certificate in
  `.platform`. Measured: refused.
- **(b) `zfs-dkms` with `sign_tool` pointed at `/var/lib/sbctl/keys/db/db.{key,pem}`.**
  Same certificate, same keyring, same refusal. §8 of `docs/secure-boot.md`
  proposed exactly this and asserted that `CONFIG_INTEGRITY_MACHINE_KEYRING`
  "accepts `db` certificates from the firmware". That assertion is **wrong** and
  has been corrected in this commit.

Neither is a packaging problem, so no PKGBUILD was written.

## What is left open

Three ways forward exist; none was implemented and none is costless.

1. **shim with a vendor certificate.** Build `shim` (in `extra`, unsigned) with
   this profile's module-signing certificate compiled in as `VENDOR_CERT_FILE`,
   sign the shim itself with the machine's `db` key — legitimate here, because
   this profile owns the firmware and does not need a Microsoft signature — and
   insert it as `firmware → shim → Limine → UKI`. shim publishes the vendor
   certificate in `MokListRT`, the kernel loads `MokListRT` into `.machine`, and
   `.machine` *is* consulted for modules. This is the only non-interactive path
   found: it needs no MokManager screen, which is what made the shim + MOK track
   unusable for a headless machine in the first place. Cost: a `shim` package, a
   changed boot chain, and a rewrite of §2 and §7 of `docs/secure-boot.md`.
2. **Our own `linux` package** with the certificate in `CONFIG_SYSTEM_TRUSTED_KEYS`.
   Correct and heavy: a full kernel build per Arch release, in lockstep, forever.
3. **Relax the module rule on ZFS machines**: drop `lockdown=integrity
   module.sig_enforce=1` from the cmdline drop-in. Secure Boot keeps verifying
   the boot chain, and the relaxation is itself inside the signed UKI, so it
   cannot be added by an attacker — but root on the running system regains the
   ability to load arbitrary modules. Honest degradation, one line, no new
   package. It is what makes the addon shippable today for anyone who wants ZFS
   more than they want that specific boundary.

Everything else the task called for was **not** started: no `zfs-utils` /
`zfs-dkms` / `zfs-linux` PKGBUILDs, no `zfs` addon, no ISO mirror bundling, no
`vm.sh --data-disk-gb`, no `acceptance-zfs.sh`, no `docs/zfs.md`, no S3
round-trip, no kernel-update rehearsal, no CI secret. The licensing note (CDDL
module distributed separately from the GPL kernel, the Ubuntu precedent) was
never written down either; it is a reason this may never be official and is part
of why the work was reprioritised.

## Limitations of what was measured

- One kernel version (`7.1.11.arch1-1`) on one machine. The behaviour is
  mainline design, not an Arch quirk, but it was not re-checked across versions.
- OVMF, not real firmware. Real firmware could conceivably route `db` differently;
  nothing in the kernel source suggests it would, since the routing is decided in
  `security/integrity/platform_certs/`, not by the firmware.
- The shim-vendor-certificate route (1) above is reasoned from shim's documented
  behaviour and was **not** tested.
